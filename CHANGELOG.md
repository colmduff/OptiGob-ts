## Unreleased

### Bug Fixes

- **Cattle "protein" was raw product mass, not protein.** `results.protein`'s cattle columns reported the `cattle` table's values unconverted, so **milk was ~28,600x and beef ~5,000x too large** — and reported under `PARAMETER_UNITS[PROTEIN] = "t"` alongside the non-cattle sectors, which really are tonnes of protein. `total_cattle_systems` (8.85e9) and `total_non_cattle_agriculture` (3.64e5) were not summable, and the stacked protein chart in `optigob_ts_app` was unreadable: milk dwarfed every other sector into a flat line.

  Root cause was twofold. The DB values are **byte-identical to OptiGob's `animal_protein_scalers`**, which declares them `unit='kg'`, `item='milk'/'beef'`, `pop=10000` (54,202,500 ÷ 10,000 = 5,420 kg milk/cow/yr) — i.e. **kg of milk and kg of beef carcass**, mislabelled `'t'` in the source spreadsheet inherited from `OptiGOBTimeSeries`. And OptiGob's protein-content conversion (`livestock/livestock_budget.py::get_total_milk_protein`, `× self._milk_protein`) had no counterpart here at all.

  Fixes:
  - The cattle metrics are **relabelled at source** in `tools/data_sources/dynamic_systems.xlsx`: `protein_milk` (t) → **`milk_yield` (kg)**, `protein_beef` (t) → **`beef_carcass_yield` (kg)**, `human_consumed_protein` (t) → **`total_yield` (kg)** (it was the raw sum of the other two — milk mass plus carcass mass — which is not a protein figure).
  - New **`protein_content`** table, copied from OptiGob verbatim (`beef 0.23`, `milk 0.035`, `sheep 0.25`, `pig 0.25`, `poultry 0.27`, `crops 0.25`), read via `DatabaseManager.get_protein_content_scaler(type)`.
  - `CattleAgriculture.get_protein()` now converts: raw kg × content ÷ 1000. Applied at **report time**, so scaling and the livestock LP are bit-identical — only protein moves. Verified against Ireland's CSO 2020 figures (8,293 M litres milk, 633,000 t beef carcass), which the raw yields match to within 3%.
  - Cattle protein is now **split by product** with distinct labels: `Dairy_milk_protein`, `Dairy_beef_protein` (dairy-origin beef), `Beef_beef_protein` (suckler). Previously `Dairy_protein_milk` and `Dairy_protein_beef` both prettified to "Dairy cattle" downstream, showing one legend name twice.
  - Non-cattle is **deliberately unchanged** — its `protein` metric is already tonnes of protein (Crops carries a distinct `human_consumed_protein`, 176,358.5 vs 271,320.8, a split that only makes sense for a protein figure). Commented in place, as it is the obvious thing for a future reader to "fix" wrongly.

  Baseline 2020 now: milk 286,821 t, dairy-beef 84,208 t, suckler beef 65,939 t; cattle total 436,968 t against non-cattle 364,294 t. New `tests/test_protein.py` (10 tests) including an order-of-magnitude guard between the two totals — the regression that would have caught this.

- **`tools/create_database.py` no longer reintroduces the deleted `co2e` rows.** The 39 precomputed `co2e` rows removed from the shipped DBs previously (unknown GWP/AR basis; `common/gwp.py::recompute_co2e` derives co2e from raw co2/ch4/n2o instead) were only deleted from the `.db` files, not from the source spreadsheets, so any rebuild silently brought them back — the caveat flagged in that entry below. They are now removed from `dynamic_systems.xlsx` itself (`cattle`, `non_cattle`, `organic_soils` sheets), making the pipeline idempotent.

- **Cattle's first waypoint no longer lands at full strength in `baseline_year + 1`.** `run_cattle_systems()` fetched each waypoint's DB reference row once and applied it to every year in the segment starting at `baseline_year + 1`, so the first waypoint's `abatement`, `productivity` and `ratio_value` all snapped to full effect in year 1 rather than phasing in. Measured on the shipped presets: **beef CO2e −14.1% across 2020→2021** on the defaults (the ratio), and **cattle CO2e −32.2%** on the dashboard's Frontier preset (abatement). Not afforestation, which is flat until 2025.

  **Deployment now runs on a fixed `baseline_year → deployment_year` clock** (new top-level config key `deployment_year`, default **2050**), deliberately independent of `target_year` and of every waypoint. This reproduces the three properties of the original OptiGob's year-indexed scaler tables (`animal_emission_scalers`, `animal_protein_scalers`): every scenario shares an identical baseline-year value, the ramp between is linear, and the horizon is fixed. Anchoring the ramp to the first waypoint instead — the obvious alternative — would make "Frontier" mean a 2030 deployment for one user and a 2050 deployment for another.

  The distinction the fix rests on: the **emissions envelope** is a *target* the user sets, so it belongs on waypoints; **technology deployment** is a *scenario property*, so it belongs on a fixed clock. The envelope's interpolation is unchanged. Result: Frontier's 2021 step is now −2.21%, and deployment intensity at 2030 is identical regardless of checkpoint placement. New `tests/test_deployment_ramp.py`; rationale in `claude-docs/abatement-deployment-ramp.md`.

- **`ratio_value` is now optional and defaults to the baseline year's own observed dairy:beef ratio** (~1.5865 in the bundled DB, recovered from the data rather than hardcoded), and **ramps** toward any configured value on the deployment clock instead of snapping in year 1. This supersedes the "mandatory" breaking change below. Mandatoriness was never what gave the LP its land-balance awareness — running the LP at all is — and forcing a value caused real harm: the dashboard defaulted to `2.0` in steps of `0.5`, so the true baseline was unreachable and every run silently restructured the herd.

### Features

- **Per-sector raw gas series**: `Results.ch4`, `Results.co2`, `Results.n2o` (kt of the gas, no GWP applied), alongside the existing `Results.ghg`. Backed by a new `Field.get_gas(gas, time_span)` / `System.get_gas(...)` mirroring `get_co2e`, with the same overrides as `get_net_zero` (forestry contributes zeros — it has no gas-level breakdown in the DB; AD sums its `additional_*` streams). `Results.ch4`'s non-total columns sum exactly to `compute_net_zero`'s `total_ch4`, which is what `check_net_zero_status`'s split-gas target is graded against — so a missed CH4 target can now be attributed to the sectors driving it.

- **Both cattle budget clamps now log a warning** when non-cattle agriculture alone exceeds the whole-agriculture envelope, naming the sector and year. Previously this clamped to zero silently and the run looked successful while solving to an empty herd.

### Breaking Changes

- **Bundled database is now `optigob_ts_default_0.1.1.db`** (`0.1.0` deleted). The cattle table's `protein_milk` / `protein_beef` / `human_consumed_protein` metrics are renamed to `milk_yield` / `beef_carcass_yield` / `total_yield` with unit `kg`, and a `protein_content` table is added — see the protein fix above. Every other table is unchanged row-for-row. Any config or caller referring to the old metric names by string (e.g. as a `scale_parameter`) must be updated; `tests/data/database.db` was regenerated to match.

- **`results.protein`'s cattle column names changed**: `<System>_protein_milk` / `<System>_protein_beef` → `<System>_milk_protein` / `<System>_beef_protein`, and the values are now tonnes of protein rather than kg of raw product. Consumers that hardcode the old names (including `optigob_ts_app`'s label map) need updating.

- **Removed the heuristic (non-ratio) cattle dairy/beef split entirely.** *(Superseded in part — see Bug Fixes above: `ratio_type`/`ratio_value` are no longer mandatory, though the heuristic remains gone.)* `ratio_type`/`ratio_value` were made mandatory on every `cattle_systems` config (block-level and/or per-waypoint) — `CattleAgriculture.run_cattle_systems()` raised `ValueError` immediately if neither resolved, instead of falling back to the old beef-cut-first/dairy-grows-first heuristic. The heuristic had no land-balance awareness at all (unlike the ratio branch's per-year `area_commitment` constraint) and was independently shown to be path-dependent (final herd composition depended on the order/severity of past waypoints, not just the current budget — `claude-docs/consistency-and-moo.md` §2a). Every existing config without a ratio needs one added; the removed branch is kept for reference in a local, gitignored `artifact/cattle_heuristic_branch.py`, not part of the package.
- **Removed `Optigob.get_evaluation()`, `Optigob.visualise()`, and `Optigob.export_time_series()`.** `Optigob.get_results()` / `results.Results` is now the one reporting API — it fixes real bugs `get_evaluation` had (field identity lost when flattening across fields, all-zero rows silently dropped) and returns pandas DataFrames organized by output category instead of raw lists. `Results.to_excel()` replaces `export_time_series()`'s raw dump with a curated export; `Results.plot(category)` replaces `visualise()`.
- **Moved `keys.py`, `utils.py`, `gwp.py`, `logger.py` into a new `common/` subpackage.** Import paths change: `optigob_ts.keys` → `optigob_ts.common.keys`, `optigob_ts.utils` → `optigob_ts.common.utils`, `optigob_ts.gwp` → `optigob_ts.common.gwp`, `optigob_ts.logger` → `optigob_ts.common.logger`.
- **`Optigob.apply_scalers()`, `Optigob.area_balancing()`, `Optigob.balance_spared_sheep_cattle_area()`, and `Optigob.balance_afforestation_organic_soils()` are no longer methods on `Optigob`.** They're now plain functions in new modules `scalers.py` (`apply_scalers(fields, db_manager, baseline_year)`) and `balancing.py` (`balance_areas(fields, baseline_year, target_year)`, plus private helpers `_balance_spared_sheep_cattle_area`/`_balance_afforestation_organic_soils`), taking their previous `self`-derived arguments explicitly. `Optigob` itself is now a thin orchestrator (`__init__`, `run`, `get_field`, `get_net_zero_calculations`, `get_results`) — calculation logic that isn't pure orchestration lives in `scalers.py`/`balancing.py`/`emissions.py`/`results.py`.

### Features

- **Net-zero / split-gas-CH4 targets**, conceptually related to `OptiGob`'s `split_gas` SIP flag but with a materially different mechanism, designed specifically for this package's waypoint/time-series model rather than OptiGob's single-target-year one.

  **Convention, applied consistently everywhere**: every scaler/fraction in this package means "fraction of baseline that remains" (matching the pre-existing `scaler` field) — e.g. `net_zero_frac=0.05` means "at most 5% of baseline may remain" (a 95% reduction). `split_gas_frac` uses this same convention.

  **Per-waypoint CH4 envelope**: cattle waypoints can now carry `ch4_scaler` (+ `ch4_scale_absolute_or_percentage`), a second budget envelope alongside the existing `scaler`/`scale_parameter`, built by `CattleAgriculture.run_cattle_systems()` exactly the same way as the `co2e` envelope — its own baseline, its own per-waypoint limit, its own anchor-tracked linear interpolation between waypoints, non-cattle-agriculture's own (exogenous, already-resolved) CH4 subtracted out the same way `nca_values` is subtracted from the `co2e` budget. This means CH4 supports multiple independent checkpoints (e.g. a 2030 target *and* a separate 2050 target) exactly like `co2e` already did — the capability gap that prompted this design. `ch4_scaler` is mandatory on every waypoint when `split_gas=True` (mirroring `ratio_type`/`ratio_value`'s mandatoriness). `LivestockOptimisation.optimise()`'s existing `ch4_budget` param (a real, independent Pyomo constraint) needed no changes — only the caller's computation of that budget changed.

  **Two independent, purely post-hoc targets**, checked only at `target_year`, unrelated to what the LP enforced along the way: `net_zero_frac` (new, default `0` — today's strict-net-zero behaviour) targets whole `co2e` if `split_gas=False`, or the CO2+N2O-only metric if `split_gas=True`; `split_gas_frac` (existing) targets whole-AFOLU baseline CH4 (every sector, not just cattle) — deliberately independent of the cattle waypoints' own `ch4_scaler`, since a scenario can hit every one of its own waypoint targets and still fail this whole-sector scorecard if those targets weren't ambitious enough. New `Optigob.check_net_zero_status(epsilon=1e-6)` returns `{"net_zero": bool, "split_gas_ch4": bool | None}` (both always computed, unlike OptiGob's single bool picked by its SIP flag; `split_gas_ch4` is `None` only if `split_gas_frac` was never configured). New `Optigob.target_achieved(epsilon=1e-6)` is the single-bool convenience on top of that, resolved automatically from `split_gas`. `tests/example.py` prints both for its plain-net-zero and split-gas re-runs.

  **Metric renamed**: `co2e_split_gas` → `co2_n2o_co2e` (the actual key/scale-parameter value, not the already-clear `results.py` column labels), since "co2e" alone doesn't communicate that CH4 is excluded.

  New tests: 4 direct-LP tests in `test_livestock_optimisation.py` (CH4 constraint binding, zero-budget, negative-budget infeasibility, no-`ch4_budget` regression pin), plus `test_net_zero_status.py` (14 tests) covering regression safety, `net_zero_frac` configurability, multi-waypoint-checkpoint CH4 enforcement (two waypoints with distinctly different `ch4_scaler` producing two distinctly different per-year slopes), missing-`ch4_scaler` validation, a feasible scenario that measurably changes the optimiser's solution, a too-tight `split_gas_frac` that fails independently of a satisfied `ch4_scaler`, `target_achieved()`'s mode resolution, and config validation.

  Every example/test-data config with `split_gas: true` (`examples/cattle_example.json` + its `tests/data/cattle/`/`tests/data/cattle_ratio/` copies, `tests/data/land_balance/input/feasible_config.json`, `examples/config.json` and its `tests/data/full_example/input/config.json`/`config_split_gas.json` copies) had its `split_gas_frac` renumbered to the new residual-fraction convention (`0.3` → `0.7`, preserving the original "30% reduction" intent) and gained `ch4_scaler`/`ch4_scale_absolute_or_percentage` on every cattle waypoint (now mandatory under `split_gas=True`) — chosen milder than the corresponding `co2e` `scaler` at each waypoint, since CH4 abatement is typically harder than CO2e broadly.
- **New land-balance enforcement**, closing the gaps documented in `claude-docs/land-balance.md`:
  - `OrganicSoilSystem.update_soil()` now validates `rewetting_ratio` is within `[0, 1]`, raising `ValueError` otherwise — previously a ratio `> 1` silently produced negative land area and sign-flipped emissions.
  - New `balancing.validate_land_balance(fields, baseline_year, target_year)`, called from `Optigob.run()` immediately before `balance_areas()`, checks that the organic-soil pool (`"Organic soil under grass"`'s baseline `Drained` area, shared between rewetting's claim — served first, unconditionally — and afforestation's organic-soil sub-claim) never goes negative at any year. On violation, raises `ValueError` naming the exact year, shortfall, and the maximum feasible `afforestation_rate` that would have worked instead (computed directly, not via a solver, since afforestation's area scales linearly in the rate; the reported value is floored, not rounded, so it's guaranteed feasible if used as-is).
  - The general grassland pool (cattle/sheep vs. afforestation+AD) needed no new validator: making `ratio_type`/`ratio_value` mandatory (see Breaking Changes) means every cattle scenario now goes through the ratio-LP's own per-year `area_commitment` constraint, which already prevents this pool from going negative by construction.
  - AD is confirmed to have no organic-soil attribution anywhere in its DB tables (`ad_biomethane_strategy`/`additional_ad`/`willow_beccs`), unlike afforestation — it only competes for the general grassland pool, not the organic-soil pool.
- **New `results.py`**: `Optigob.get_results()` returns a `Results` object exposing output-category properties as pandas DataFrames — `.area`, `.ghg`, `.protein`, `.biodiversity`, `.energy`, `.hwp`, `.substitution`, `.livestock_population` — plus `.net_zero()`, the lower-level `.wide(parameter, field=None, include_totals=False)`, `.to_csv()`/`.to_excel()`, and `.plot(category, ax=None, include_totals=False)` for a quick matplotlib chart (lazy `matplotlib`/`openpyxl` imports, same optional-extras pattern as the methods they replace). Built on one internal long/tidy DataFrame that defends against two real data quirks uniformly: `AnaerobicDigestion`'s raw `time_series` arrays are always 81 years (2020–2100) regardless of `target_year` (sliced to `time_span` unconditionally), and `is_total` row detection is structural (last element of a field's returned list, if its label starts with `"total_"`) rather than name-matching, since `AnaerobicDigestion` hardcodes the literal `"total_ad"` and `OrganicSoils` never appends a total row at any grain.
- New `CattleAgriculture.get_livestock_population(time_span)` exposing Dairy/Beef head counts (`total_cattle_numbers`) plus a field total — previously only reachable by indexing raw `time_series` directly; now surfaced through `Results.livestock_population`.
- Rewrote `tests/example.py` as a single canonical walkthrough of the category-based `Results` API (prints each category's DataFrame, plots GHG and area, exports the full `Results` via `to_excel()`), and added `tests/test_land_balance.py` plus a `rewetting_ratio` bounds test in `tests/test_organic_soils.py`. Removed two Results-specific example scripts (`tests/results_example_test.py`, `tests/cattle_ratio_results_example_test.py`) that were written against an intermediate, field-based `Results` design (one subclass per internal `Field` type) since abandoned in favor of the flat, category-based one — that intermediate design mirrored the simulation's internal sector classes rather than the kinds of output someone actually wants to look at, and most of its subclasses ended up empty.
- **`balancing.py`, `systems/livestock_optimisation.py`, and `systems/cattle_agriculture.py` now log their own internals** via `common/logger.py` — `validate_land_balance()`/`balance_areas()` and their private helpers log which pools/functions ran or were skipped (INFO) and the full per-year claim/balance arithmetic (DEBUG); `LivestockOptimisation.optimise()` logs its inputs (DEBUG) and, on success, the solved `dairy_scaler`/`beef_scaler`, the *achieved* ratio computed from them against the configured `ratio_value`, and how much of the area/emissions constraints were used (INFO); `run_cattle_systems()` logs the resolved `ratio_type`/`ratio_value` per segment (INFO) and `year_budget`/`area_commitment` per year (DEBUG). Added so these modules are inspectable end-to-end with `configure_logging()` alone, without external instrumentation.
- New walkthrough scripts `tests/land_balance_example_test.py` (steps through `balancing.py`'s two entry points by hand — `validate_land_balance()` then `balance_areas()` — against a feasible scenario, then two deliberately-infeasible ones, printing before/after snapshots) and `tests/cattle_ratio_example_test.py` (confirms the ratio-constrained cattle optimiser two ways: reading the new internal log lines, and independently re-fetching the same DB reference rows to recompute `dairy_scaler`/`beef_scaler` from the output time series and cross-check the achieved ratio against `ratio_value`, across the `cattle_example.json` scenario's dairy_per_beef→beef_per_dairy flip).
- **Every runnable walkthrough script now has its own `tests/data/<name>/{input,output/{figures,excel,logs}}/` folder** (`land_balance`, `cattle_ratio`, `cattle`, `forestry`, `non_cattle_agriculture`, `organic_soils`, `ad_emissions`, `full_example`) — `input/` holds a copy of that script's config JSON (`examples/*.json` originals are kept too, since `claude-docs/` cross-references those paths directly), and `output/` collects that run's figures, excel exports, and a freshly-truncated log file per run. Added excel export to `land_balance_example_test.py`, `cattle_ratio_example_test.py`, and `cattle_example_test.py`, which previously had none. Removed the now-superseded `examples/plots/` directory.
- Added an opt-in, ratio-constrained livestock optimiser (Pyomo/HiGHS) for the cattle dairy/beef split, alongside the existing heuristic — activated per-waypoint via `ratio_type`/`ratio_value` (`systems/livestock_optimisation.py`, wired into `systems/cattle_agriculture.py`). *(The heuristic alternative this shipped alongside was later removed and the ratio branch made mandatory — see Breaking Changes above.)*
- The ratio-optimiser branch now solves independently for every year within a waypoint's segment (not just at the waypoint), enforcing that year's real sibling-sector land use as a hard `area_commitment` constraint alongside the emissions budget.
- Added standalone example configs and narrative walkthrough scripts for every module — forestry, non-cattle agriculture, organic soils, AD emissions, and cattle (with the new ratio optimiser) — under `examples/` and `tests/*_test.py`, each producing a matplotlib chart (now saved under each script's own `tests/data/<name>/output/figures/`, see above).
- Made GWP/AR handling configurable and extensible: `gwp.py` adds a `GWPValues` dataclass and an AR4/AR5/AR6 registry (real IPCC GWP100 values), replacing the previous hardcoded CO2e formula (`co2 + 260*n2o + 25*ch4`, which matched no published AR). Selectable per run via an `"AR"` key in `json_config` (defaults to `"AR5"`, a behaviour change from the old formula's implicit constants).
- Eliminated reliance on the DB's precomputed `co2e` column wherever a CH4/N2O/CO2 breakdown exists to recompute it from (`gwp.py`: `recompute_co2e()`), since that column's original GWP/AR basis is unknown and unrecoverable: cattle, non-cattle agriculture, and organic soils now always derive `co2e` from raw gases via the selected AR, both at baseline load and at every waypoint re-fetch. Because `co2e` is also the scaling currency for waypoint budgets (`scale_parameter="co2e"`) and the ratio-optimiser's emissions constraint, this changes the *entire* scenario's output for these sectors under a non-default AR (cattle numbers, protein, etc.), not just the reported CO2e figure — see the recomputed hardcoded expectations in `tests/test_cattle_agriculture.py`, `tests/test_non_cattle_agriculture.py`, and `tests/test_livestock_optimisation.py`. AD emissions were already fully gas-driven (its DB tables never stored a `co2e` column to begin with).
- Removed the now-redundant precomputed `co2e` metric rows (39 total: 19 cattle, 13 non-cattle, 7 organic soils) from both `src/optigob_ts/database/optigob_ts_default_0.1.0.db` and `tests/data/database.db`, since nothing reads them anymore and their unknown GWP/AR basis made them actively misleading to keep around. Verified safe (full test suite and all example scripts unaffected) before deleting; `.db.bak` copies of both files were kept alongside the originals as a safety net, since this repo has no commit history yet to fall back on. **Caveat**: `tools/create_database.py` regenerates these DB files from source Excel spreadsheets and was not modified — if that pipeline is ever rerun, these `co2e` rows will likely reappear, since the tool just melts whatever's in the source spreadsheet. That pipeline needs its own fix if the source data itself should stop carrying a precomputed `co2e` column.
- **Permanent limitation, not fixable in Python**: forestry (`existing_forest`/`afforestation`), HWP, substitution credits, BECCS, and willow do not respond to the AR selection and never can from this codebase alone. Their DB tables (`existing_forest`, `afforestation`, `willow_beccs`) store only pre-aggregated stock-change/lifecycle figures (`ghg_fluxes`, `hwp_c_storage`, `beccs`, `hwp_material_substitution_credit`, `hwp_energy_substitution_credit`, `lulucf_co2_emissions_credit`, `co2_substitution_credit`) with no CH4/N2O/CO2 breakdown at all — there is no GWP hidden inside these numbers to swap out, because none was ever applied to a gas-level split. Any AR-dependence here would have to be resolved upstream, by rerunning the source carbon-accounting model (FERS-CBM-equivalent) with gas-level outputs.

### Bug Fixes

- **Fixed bug #11: forestry silently misaligning when `baseline_year` != the database's first year.** Forestry reads its whole year-ordered trajectory and treats row 0 as the baseline, while every other sector anchors to the config's `baseline_year`; if the two disagreed, forestry's series shifted against everything else with no error. `Optigob.__init__` now validates that `baseline_year` equals the database's first year (new `DatabaseManager.get_baseline_year()`, `MIN(year)` from `existing_forest`), raising a clear `ValueError` on mismatch. Forestry's own series handling is deliberately untouched (a single-year filter would break the time-series model), so the default `baseline_year=2020` behaviour is byte-identical. A `baseline_year` later than the DB's first year (a shifted afforestation-ramp anchor) remains unsupported by design. New `tests/test_baseline_year.py`.
- Fixed `CattleWayPoint.get_data()` always using `dairy_productivity` for both the Dairy and Beef DB lookups; `beef_productivity` is now honoured for Beef.
- Fixed a land-balance bug where cattle's committed area could exceed what was actually available in years between waypoints, when forestry/sheep/AD land claims outpaced cattle's own waypoint-interpolated reduction (see the per-year solve above). Originally scoped to the opt-in ratio branch only; fully closed once ratio became mandatory (see Breaking Changes).
- Fixed the displayed "max feasible `afforestation_rate`" in `validate_land_balance()`'s error message using round-to-nearest formatting, which could itself be infeasible if used as-is (e.g. displaying `20.4` when the true maximum was `20.3993`, so re-running with the displayed value still raised). Now floored to 4 decimal places instead — confirmed by a dedicated regression test that re-runs with the exact reported value.
- Fixed `tests/example.py`'s `run_ratio_demo()`, which had gone stale: it re-ran with `ratio_type="dairy_per_beef", ratio_value=2.0`, identical to what `examples/config.json`'s `cattle_systems` block already sets now that the heuristic split is gone (see Breaking Changes), so the "demo" was a no-op re-run, and its comments still described the removed heuristic. Now uses `ratio_value=5.0` so it actually demonstrates a different split, with comments updated to match current behaviour.
- Fixed `tests/example.py`'s split-gas re-run block, added alongside the net-zero/split-gas-CH4 feature above: its closing `run_ratio_demo(config, logger)` call (and the printed `ratio_type`/`ratio_value` label just above it) referenced `config` — the plain net-zero config from earlier in `main()` — instead of `config_split_gas`, so the split-gas ratio-demo was silently re-solving the wrong scenario a second time (its output was byte-identical to the net-zero ratio-demo run immediately above it). Both now reference `config_split_gas`; confirmed the two ratio-demo blocks produce genuinely different numbers.

### Known issues

- **Near-term (2020-2025) scaler calibration is inert, and the obvious one-line "fix" is a trap (bug #3).** `AgricultureSystem.update_by_scaler` uses a strict `type(x) is float` check that a `numpy.float64` (the `scalers` table's dtype) fails, so only the first (2020) row ever applies and every later year is frozen flat — the mechanism currently does nothing. Switching the check to `isinstance(x, float)` activates the loop but exposes a deeper bug: `update_by_scaler` re-reads the already-scaled `value[0]` and re-multiplies it each year, sending Dairy `co2e` to ~2,000,000 kt/yr. The full-run outputs stay near-sane only by accident (the cattle optimiser recomputes cattle from scratch, and non-cattle scalers are ~1.0), so this must not be "fixed" naively. A correct fix needs the intended calibration semantics defined and `update_by_scaler` reworked to scale a pristine per-unit baseline; deferred and best coordinated with the baseline cattle N2O review (#12), since both touch the early-year cattle numbers. Left inert (current tested behaviour) for now. See `claude-docs/bugs.md` item #3 and the `scalers.py` docstring.
